# PM

PM semantics over the built-in kinds: what a `story`, `epic`, `sprint`, and `plan` *mean*. The kind registry ([[spec:kind-builtin-pm-set]]) owns the entries — fields, states, the column-state mapping; this doc wires them into boards. Everything here is a consumer of existing substrates: the board surface (`kanban.md`), the trail-style ordered-refs pattern ([[spec:kind-shapes]]), and the metadata index ([[spec:store-note-metadata-index]]). One new `core::pm` module owns the PM-specific reads and ops; sprint acceptance lands in `core::boards`' parse gate.

The headline decisions:

- A work note's status is **derived, never stored**: its column in its one sprint-kind board, read through the kind's column-state map ([[spec:kind-column-state-map]]). Membership in at most one sprint is enforced at every card-add op; every other board a note appears on is a view with zero PM semantics. [derived-status-rule]
- **Sprint is a board subtype**: the board parse gate accepts any registered board-like kind alongside `board`, so the whole existing board surface — view, ops, WIP limits, DnD, MCP staging, the `board_cards` table, rename sweeps — works on sprints unchanged. [sprint-board-subtype]
- **Epic is a list-like container** of work-note refs; progress is a rollup over members' derived statuses, counted by category anchor ([[spec:kind-state-categories]]). [pm-epic-rollup] A derived `list_refs` table mirroring [[spec:board-cards-derived-table]] backs the rollup and the reverse "epics containing this story" lookup. [pm-epic-derived-table]
- **Sprint close is one staged batch**: every card outside a `done`/`canceled`-category column moves to the next sprint or the plan's backlog board, staged for review like any machine-computed bulk edit ([[spec:op-log-reorg-batch]]). [sprint-rollover]
- **Plan is the root container** grouping epics, sprints, and a backlog board; it owns policy *defaults* only (default kind, rollover destination) — the column-state map lives on the kind per [[spec:kind-column-state-map]], never on a plan. [plan-kind]
- **Metrics replay the snapshot history**: burnup, cycle time, and velocity are derived from the sprint board-doc's plain-file snapshots (`op-log.md` "Local history") joined with `estimate` fields, rendered via hiker-charts. No new tracking writes, no event table. (Fidelity is bounded by snapshot retention — accepted.) [pm-oplog-metrics]


## Story and task

A story (or task — two names, one definition per [[spec:kind-builtin-pm-set]]) is a leaf note: typed fields (`priority`, `due`, `estimate`) are plain frontmatter keys indexed through [[spec:store-note-metadata-index]], and the body is the description — freeform markdown, never machine-written. A story carries no status field, no sprint pointer, and no board reference; everything positional about it is owned by the boards and epics that reference it, so the note itself stays an ordinary markdown file that any editor can touch. ## Sprint as a board subtype

A sprint is a board-doc whose discriminator is `hiker.kind: sprint` instead of `board`. The parse gate (`boards::parse_board_for`, `.md` rule included) extends to accept any kind the registry declares `board-like` — the acceptance set is `{ "board" } ∪ registry board-like kinds`, threaded from the compiled registry the indexer already carries (`JobCtx.kinds_cell`). Acceptance is shape-driven, not sprint-special-cased, per `kinds.md`'s parse-gate paragraph. ### Derived status

A work note's status is a *read*, computed from `board_cards` plus the registry: find the note's cards on sprint-kind boards (board kind read off `note_meta`, the same join the query grammar's `category` clause compiles through), take the one sprint, map its column through the kind's column-state map — the mapped state is the status, the state's category is what rollups and automation consume. No `status:` frontmatter exists anywhere; there is exactly one source of truth and zero reconciliation. A note in an unmapped column, or on no sprint at all, has no derived status — rollups count it under the `backlog` category. [derived-status-rule]

**At most one sprint.** Enforced where membership is written — twice. At stage time, the card-add paths (`boards::ops::add_card`, the shared `apply_edit` mutation step the MCP write tools route through, and the board-pane drop target) refuse to add a note card to a sprint-kind board when the note is already a card on a *different* sprint-kind board, naming the holding sprint in the error. And at apply time: accepting a staged card-add re-checks membership against the accepted state at the moment of the flip (the checked flip seam, `op_writes::flip_*_checked` → `pm::verify_flip_single_sprint`), closing the review-mode hole where two staged adds to different sprints each passed at stage time — the second accept is refused with a typed error and stays pending. Plain-board membership stays unconstrained ([[spec:board-many-to-many]] is untouched — a story on a roadmap board and a personal board simultaneously is the intended shape; those boards just carry no PM meaning). Ingest never rejects: a hand-edited double membership indexes normally (lenient, per the [[spec:kind-lenient-validation]] posture), and the derived-status read returns an explicit conflicted outcome rendered as a problem pill on both sprints' cards until the user removes one.

Tradeoff — enforcement at the op, not the parser: refusing at parse time would make a hand-edited file invisible (data dropped), violating markdown-first. The op-level check catches every path hiker controls; the conflicted read catches the rest loudly.

### Close and rollover

Closing a sprint is one staged operation: a **Close sprint…** entry in the sprint board's header menu picks a destination — another sprint-kind board (defaulting to the plan's next sprint by `start` date when the sprint belongs to a plan) or the plan's backlog board — then stages, as a single batch, (a) the destination board-doc gaining every card from the closing sprint's non-`done`/`canceled`-category columns (appended to the destination's first `todo`-category-mapped column, else its first column), (b) the closing board-doc losing those cards, and (c) `closed_at: <iso8601>` stamped into the closing board-doc's frontmatter — the marker that guards double-close and tells metrics where the sprint ended. Unmapped-lane cards roll over too: only `done`/`canceled`-category columns keep their cards, so unfinished work can never silently vanish into a closed sprint. Freeform cards ([[spec:board-freeform-card]]) follow the same column rule. [sprint-rollover]

## Epic

An epic is a list-like note ([[spec:kind-shapes]]): an ordered `refs` list of `{ path }` entries in frontmatter naming its member work notes, body is prose framing — the trail-doc split, with path-as-identity and the shared rename-rewrite pass ([[spec:wikilink-rename-rewrite]]) keeping refs current when members move. Progress is a **rollup over members' derived statuses**: per-category counts (and `estimate` sums) computed by running the derived-status read over the member set — an epic never stores progress, so it can never disagree with the boards. Members with no derived status count under `backlog`. [pm-epic-rollup]

## Plan

A plan is a list-like root container: its `refs` are the plan's epics and sprints (ordered, the plan's own presentation order), and its policy lives in plain frontmatter keys on the plan note — `default_kind` (the kind a note born inside this plan gets) and `backlog` (`{ path }` of the plan's backlog board, the rollover destination of last resort). The built-in `plan` entry declares no fields ([[spec:kind-builtin-pm-set]]), so these keys are unvalidated extra frontmatter in v1; a vault that wants them typed and tool-exposed adds them to its registry entry — the registry is user-editable by design. A plan owns **defaults only**: it never carries a column-state mapping (that lives on the board-like kind per [[spec:kind-column-state-map]]), never stores member status, and never gates board ops. A board or epic belongs to a plan iff the plan's refs (or its `backlog` key) name it — membership is plan-owned, read through `lists_containing_note`. [plan-kind]

## Promote a freeform card

Every board — plain or sprint — gets a **Convert to note** verb in the freeform card's context menu (menus per [[spec:rightclick-menu-always]]): create a note from the card's text (first line slugified as the filename, suffix-on-collision; full text as the body), then swap the card in place — same column, same position — from `{ card_id, text }` to `{ path }` in the same user-initiated commit. The note lands in the board-doc's directory, visible and movable like any note (the rename-rewrite pass keeps the card pointing if it's moved). When the board belongs to a plan declaring a `default_kind`, the note is born with that kind: `hiker.kind` set and the kind's fields seeded empty — the freeform-sticky-to-story onramp. ## Metrics from the snapshot history

Every card move is a save on the board-doc, and every save writes a plain-file snapshot ([[spec:plain-file-snapshots]]), so the sprint's snapshot history *is* the tracking data. Metrics are derived by **replaying the board-doc's snapshots**: walk `op_writes::snapshot_history(board_path)`, read each snapshot via `content_at_snapshot`, parse it with the board parser, and diff consecutive column memberships into `(card, column, timestamp)` transition events; map columns to categories through the kind's column-state map; join `estimate` per card from the metadata index. Nothing writes: no event table, no tracking hooks. [pm-oplog-metrics]

|---|---|
| burnup | per day in the sprint's `start`..`end` window (frame timestamps when dates are unset): cumulative count + `estimate` sum of cards in `done`-category columns, against the total in the sprint |
| cycle time | per card: first entry into an `in_progress`-category column to first entry into a `done`-category column; rendered as a distribution |

Rendering rides **hiker-charts**: a Metrics entry in the sprint board's header menu toggles a chart strip, built as in-memory `ChartSpec` + `Table` pairs painted through the existing theme bridge (`app/src/charts.rs::hiker_to_chart_theme`) — the same path the charts tab uses, no new chart machinery.

Honest bounds, stated up front: history is per-save and an identical-content save mints no snapshot, so burst moves collapse — fine for day-granularity charts. Estimates are joined at *computation* time from the current index, so editing an estimate retroactively re-weights past charts (acceptable). And the replay window is bounded by retained snapshots — the `[history]` cap (default keep-50 / 30-days) trims old snapshots, so old sprints' charts degrade to whatever snapshots survive; vaults that care about long-horizon metrics keep `[history]` retention long (or use git, whose commit graph is the durable history). Degradation is **counted and surfaced, never silent**: `SprintTables` carries `skipped_unretained` / `skipped_unparseable` counts off the replay, the strip renders a "history truncated: N snapshot(s) unavailable" marker when nonzero, and a truncated burnup starts its series at the first *retained* snapshot instead of zero-filling the unseen pre-retention days. A failed replay renders a loud, distinct error line — never the benign "No metrics yet" empty state — and velocity's close fallback logs a warning naming the sprint.

## Out of scope

- **The kind entries themselves.** Fields, states, categories, the column-state map, validation, generated tools — all `kinds.md` ([[spec:kind-registry]] and siblings). This doc consumes, never redefines.
- **Plain boards.** Zero PM semantics, unchanged forever — curation stays sacred (`kanban.md` Out of scope says the same from its side).
- **Automation rules.** Triggers on derived status / fields ("when a card enters Done, …") are the rules layer's problem; it consumes the derived-status read defined here.
- **Smart columns.** Board-lane presentation of a query is a later layer over the saved-query primitive (`queries.md` Out of scope), not a sprint feature.
- **Time tracking.** No timers, no work logs; cycle time from snapshot replay is the ceiling of v1's instrumentation.
