# Canvas

An editor and renderer for the **JSON Canvas** open format (jsoncanvas.org 1.0): an infinite spatial canvas of nodes (text / file / link / group) connected by edges. A `.canvas` file is a first-class vault document — it opens in its own tab, edits ride the op-log like a note, and it syncs across devices. The work splits an egui-agnostic document core (`hiker-canvas`) and an egui-free view+interaction layer (`canvas-view-core`) from a thin egui shell (`canvas-view`), mirroring the editor's `editor-core` / `editor-view` / `editor-egui` precedent — all under one `hiker-canvas/` directory.

The headline decisions:

- **Four layers, mirroring the editor stack** (`editor-core` / `editor-view` / `editor-egui`), all under one `hiker-canvas/` directory so the family can be lifted into a standalone repo. `hiker-canvas/core` (crate `hiker-canvas`) is the egui-agnostic document core: the serde JSON Canvas model, geometry (bounds / hit-testing / z-order), and pure edit operations. `hiker-canvas/view-core` (crate `canvas-view-core`) is the **egui-free** view+interaction layer — pan/zoom camera, edge routing, handle geometry, pointer hit-testing, gesture→`EditOp` decisions, selection, and the undo stack — depending only on `emath` (egui's math types, no rendering) plus the core, so it is unit-testable without a UI and reusable by a non-egui frontend. `hiker-canvas/view` (crate `canvas-view`) is the thin egui shell: the painter, the `CanvasView` `show` loop, pointer event plumbing, and the `NodeContentRenderer` content seam — the only crate that depends on `egui`. The `app` canvas panel glues them: tab + nav, the op-log binding, and the node-content engines (injected through the seam, so the content engines never leak into the widget crates). [canvas-crate-split]
- **A `.canvas` file is a first-class op-log document.** It rides op-log's whole-file-as-one-`Y.Text` substrate (`op-log-yrs-backed`) exactly like a note — bootstrapped, versioned, synced — under a new `canvas` document kind. The file's JSON text *is* the `Y.Text`; there's no structural CRDT modeling of nodes. [canvas-doc-kind]
- **Edits localize through canonical JSON serialization.** The model serializes to deterministic, stable-key, pretty-printed JSON so that a single node move rewrites only that node's bytes. A canvas edit produces the new serialization, diffed against `materialize(accepted + working)` into minimal localized text ops on the `working` layer — the kanban `board-move` model. Concurrent edits on different nodes merge automatically; two devices moving the *same* node surface as a conflict hunk (`op-log-merge-conflict`). [canvas-canonical-json, canvas-oplog-binding, canvas-conflict-merge]
- **Full interactive editor in v1.** Select (single / multi / marquee), move, resize, create nodes of every type, draw and re-anchor edges, edit text, pan and zoom. Undo/redo is an in-session edit-op stack; Save commits `working` to disk. [canvas-edit-ops, canvas-selection, canvas-undo-redo]
- **Inserting vault content is the primary workflow.** A canvas mostly assembles things that already live in the vault — notes, PDFs, images, captured pages. Inserting one drops a *pointer* (a file node holding the vault path), never a copy of its text; the canvas renders a live view of the referenced content. Three entry points: an **Insert from vault** picker (autocomplete-driven), a right-click **Add to canvas** verb on vault rows (mirroring `board-add-card`), and file-tree drag (deferred). Arbitrary text / group / link elements are created the same one-click way. [canvas-insert-from-vault, canvas-add-to-canvas-verb, canvas-node-create]
- **Node contents reuse the existing engines.** Text nodes render markdown through the editor widget (`editor-egui` + the live-preview decoration providers); file nodes embed the referenced vault file by type — markdown (incl. extract sidecars) / image / a vault-internal `.html` page through the no-JS `hiker-htmlview` renderer / code. Link nodes are a card that opens the URL in the OS browser — hiker never live-fetches or renders an external web page inside a canvas. The adapter never depends on those engines directly — the app injects them through a `NodeContentRenderer` seam. [canvas-node-content-trait, canvas-text-node-markdown, canvas-file-node-embed, canvas-link-node-card]
- **Canvas / JSON toggle over one document.** A "View as: Canvas / JSON" control flips the pane between the spatial editor and the raw `.canvas` text in the standard editor widget (JSON syntax via `tree-sitter-json`) — one underlying op-log document, mirroring the board view's `board-view-toggle`. [canvas-view-toggle]
- **Select / Hand tools with universal pan shortcuts.** A toolbar toggle (and the `V` / `H` keys) switches between the **Select** tool — the default, where a left-drag routes by what's under the cursor (empty canvas marquee-selects, a node moves, a handle resizes) — and the **Hand** tool, where any left-drag pans. Regardless of tool, holding **Space** while dragging or dragging with the **middle mouse button** pans, with the cursor showing the grab hand. Scroll / pinch zoom toward the cursor either way. The active tool is `CanvasView` view state — never serialized, never in the op-log. The default Select tool replaces the old plain-drag-pans behavior; pan now lives on the Hand tool, Space-drag, and middle-drag. [canvas-tool-mode]
- **Group containers are first-class, manipulable nodes.** A group is grabbed and moved by its **label/header strip** — so clicking its interior still targets the children it frames — resizes with the same eight handles as any node (reframing the container, not its members), and is created by **dragging out its rectangle** (or a bare click for a default-sized frame). Selecting a group folds its geometrically-contained children into the selection, so everything that will move is visibly selected; the moved set is exactly that selection, frozen at drag-start (`canvas-group-move`). [canvas-group-grab, canvas-group-resize, canvas-group-draw]


## Format model

`hiker-canvas` holds the JSON Canvas 1.0 schema as serde types — the egui-agnostic source of truth every layer reads. [canvas-spec-model]

```rust
pub struct Canvas {
    pub nodes: Vec<Node>,
    pub edges: Vec<Edge>,
}

pub struct Node {
    pub id: String,                 // unique within the canvas
    pub kind: NodeKind,             // serde tag: "text" | "file" | "link" | "group"
    pub x: i64, pub y: i64,         // top-left, infinite integer coordinate space
    pub width: i64, pub height: i64,
    pub color: Option<Color>,
}
```

- **Node kinds.** `Text { text }` (markdown), `File { file, subpath }` (vault-relative path + optional `#heading` / `#^block`), `Link { url }`, `Group { label, background, background_style }`. The kind tag and its extra fields flatten into the node object per the spec. [canvas-node-types]
- **Edges.** `{ id, from_node, from_side?, from_end?, to_node, to_side?, to_end?, color?, label? }` — `*_side` is `top|right|bottom|left`, `*_end` is `none|arrow` (default `to_end = arrow`). An edge whose endpoints don't resolve to live node ids is a dangling edge, surfaced as broken rather than dropped silently. [canvas-edge-model]
- **Color.** Either a preset slot `"1".."6"` (mapped to theme tokens at render time, not hard-coded hex) or a `#RRGGBB` literal. One `Color` enum covers both; presets resolve through the active theme so a canvas reads correctly in light and dark. [canvas-color-model]

**Unknown-field tolerance.** Unrecognized top-level, node, and edge keys round-trip untouched (serde `flatten` capture), so a canvas authored by another tool isn't lossily rewritten on the first edit — the same posture op-log holds for note bytes (`op-log-disk-canonical`).

**Canonical serialization.** `Canvas::to_canonical_json` emits stable key order and fixed pretty-print formatting; node and edge arrays preserve document order, and an edit mutates one element in place. This determinism is load-bearing: it's what makes a node move a localized text diff rather than a whole-file rewrite, which is what makes concurrent edits mergeable in the op-log. [canvas-canonical-json]


## Geometry and edit operations

Both egui-free, in `hiker-canvas`, so they're testable without a UI and reusable by a future headless consumer (export, MCP).

- **Geometry.** Node bounds, point/rect hit-testing, top-most-at-point with array order as z-order (later in the array paints on top), canvas content bounds (for zoom-to-fit), and the per-side anchor points an edge attaches to. [canvas-geometry]
- **Edit operations.** Pure `Canvas -> Canvas` (or in-place mutation) verbs: `move_nodes`, `resize_node`, `add_node`, `remove_nodes` (with cascade removal of incident edges), `add_edge`, `set_edge_endpoint`, `set_text`, `set_color`, `set_label`. Each returns enough information for the binding to re-serialize and for undo to invert it. No verb reads or writes any referenced note. [canvas-edit-ops]


## Render adapter

`canvas-view` (`hiker-canvas/view`) — the thin egui shell over the egui-free `canvas-view-core`, depending only on egui (plus the two canvas crates). It paints and routes egui input into `canvas-view-core`'s hit-testing / gesture logic; the host owns the clip rect, the same division `zim.md` uses for the htmlview tab. [canvas-render-widget]

**Card content is display-only.** A read-only card renders its body through the content engine in the editor widget's non-interactive (`interactive(false)`) mode, and the canvas allocates its click/drag interaction surface ON TOP of that content. So the canvas — never the content widget — owns resize / move / select / connect, and dragging a node across a card never text-selects inside it. This is the load-bearing contract that lets the spatial gestures work uniformly over every node kind. [canvas-render-widget]

- **Pan and zoom.** An infinite canvas with a viewport transform (pan offset + scale). Panning is the Hand tool, a held **Space**-drag, or a **middle-mouse** drag (`canvas-tool-mode`) — not plain left-drag, which marquee-selects under the default Select tool. Scroll/pinch zooms toward the cursor; a "zoom to fit" command frames all content via `canvas-geometry`'s content bounds. Camera state is view state, not document state — it never enters the op-log. [canvas-pan-zoom]
- **View state persists across close/reopen and restart.** Camera pan/zoom + per-card scroll/zoom survive a canvas tab close→reopen and an app restart, riding the tab-state store keyed by canvas path — NOT the op-log / `.canvas` file (consistent with `canvas-pan-zoom`: the camera is view state and never enters the op-log). Captured on tab close and on the exit/autosave tab-state snapshot, applied once to each pane on first creation (a restored camera wins over fresh-create framing). [canvas-view-state-persist]
- **Edge routing.** Edges draw from the `from_side` anchor to the `to_side` anchor as curved connectors with arrowheads per `*_end`; when a side is unspecified the router picks the facing side from relative node positions. Edge labels paint at the midpoint. [canvas-edge-routing]
- **Node frames.** Each node paints a rounded card: border + fill from its `Color`, group nodes paint a translucent background + label behind their members, selection paints handles. Node *content* is delegated (see below) — the frame layer never knows what a text or file node contains. [canvas-node-frame]
- **Background grid.** An optional dotted/grid background scaled with zoom, for spatial reference. [canvas-grid-background]
- **Viewport culling.** Only nodes and edges intersecting the visible viewport paint and hit-test, so a large canvas pays for what's on screen — the same viewport-scoping discipline the editor widgets use (`widget-render-viewport-scoped`). [canvas-viewport-cull]
- **Level-of-detail placeholder.** Below a readable on-screen size a card skips the content engine entirely and paints a cheap placeholder — a one-line title (file basename / first text line / link host) plus a few skeleton bars — instead of laying out and painting its full body. This is what keeps a zoomed-out many-document canvas smooth (a fit-to-view of 100+ file cards drops from tens of ms/frame to sub-ms, since geometric culling alone leaves every card "visible" at fit). A placeholder has no scrollable content, so a wheel over one passes through to camera zoom (`canvas-card-scroll`) rather than being captured — otherwise a tiny card crossing under the cursor mid-zoom would stall the zoom. [canvas-lod-placeholder]


## Interaction

Driven by the adapter, applied through `hiker-canvas`'s edit ops, committed by the app's op-log binding.

- **Tool modes.** Two interaction tools, toggled from the toolbar or with `V` (Select) / `H` (Hand). **Select** (default) routes a left-drag by what's under the cursor — empty canvas marquee-selects, a node body moves, a resize handle resizes, a connector handle draws an edge. **Hand** routes every left-drag to a camera pan and suppresses select/move/marquee. Independent of the tool, holding **Space** during a drag or dragging with the **middle mouse button** pans, and the cursor shows the grab / grabbing hand while it does. The active tool is `CanvasView` view state — it never enters the op-log or the `.canvas` file, the same posture as the camera. [canvas-tool-mode]
- **Selection.** Click selects a node or edge; shift-click extends; under the Select tool a drag on empty canvas marquee-selects; Esc / empty-click clears. Multi-select moves and deletes as a group. [canvas-selection]
- **Move.** Drag a selection to reposition. A group node is grabbed by its **label/header strip** (a band along its top edge) rather than its interior, so a drag inside the frame still targets the framed children. Selecting a group folds in its geometric members (the nodes whose bounds sit inside the group's rect) at *select-time*, so the selection visibly shows everything that will move; the moved set is exactly that frozen selection and is never recomputed mid-drag, so dragging a group past another group never grabs the other's cards. [canvas-node-move, canvas-group-move, canvas-group-grab, canvas-selection]
- **Resize.** Eight handles on a single selected node — including group nodes — rewrite `width`/`height` (and `x`/`y` for top/left handles). Resizing a group reframes the container only; its members keep their positions. [canvas-node-resize, canvas-group-resize]
- **Hover affordance on handles.** When the pointer is in range of an interactive handle it gets a subtle hover indicator so the grab target is obvious before pressing: a resize handle and a connector handle grow slightly under the cursor, and a group's header grab-strip (`canvas-group-grab`) highlights (a brighter band) on hover. Pure visual feedback driven by the same hit-tests the press path uses — no state change. [canvas-handle-hover]
- **Create elements.** A toolbar verb per arbitrary kind drops a node at the **viewport center** immediately — one click, no arm-then-place gesture — and selects it so it can be dragged into position: an empty text node (enters edit) or a link (a small URL prompt). [canvas-node-create]
- **Create a group by drawing it.** The "Add group" verb arms a one-shot draw mode; the next left-drag on empty canvas rubber-bands the group's rectangle (live preview) and creates the group at those bounds on release, the standard container gesture. A bare click (no drag) drops a default-sized frame instead, so the one-click path still works. Arming the draw temporarily overrides the Select tool's marquee for that one creation. [canvas-group-draw]
- **Insert from vault.** The primary workflow: an **Insert from vault** action opens an autocomplete picker (the shared autocomplete package, `autocomplete.md`) over vault notes + sources; choosing one drops a *file-node pointer* at the viewport center that renders the referenced content. A right-click **Add to canvas** verb on a file-tree row (and on a multi-selection) does the same against a chosen target canvas, mirroring `board-add-card`. The inserted node stores only the vault path — never the content. Dragging a row from the file tree onto the canvas is the deferred third gesture (`canvas-dnd-add`). [canvas-insert-from-vault, canvas-add-to-canvas-verb]
- **New note on the canvas.** A right-click empty-canvas **New note** verb mints a fresh vault note (the shared `create_new_note` path — suffix-counted `new-note-N.md`, indexed, no tab opened) and drops a `File` pointer node to it at the viewport center, ready to inline-edit. The **Cmd/Ctrl+N** binding routes here when a canvas tab is active (the same helper); on any other tab it opens a new note in a tab instead. [canvas-new-note]
- **Edges.** Hovering (or selecting) a node reveals four connector handles — small circles floating just outside its edges, clear of the resize handles. Clicking one starts a click-to-connect gesture (a rubber band tracks the cursor); the next click on a node attaches the edge. Press-dragging a handle connects the same way in one gesture; dragging an existing edge endpoint re-anchors it to a different node/side; dropping on empty canvas cancels. Double-clicking an edge opens an inline label field at its midpoint. [canvas-edge-draw, canvas-edge-redirect, canvas-edge-label]
- **Card content: scroll & zoom.** A card is a fixed window into its content, *decoupled from camera zoom* — the body renders at a per-card content zoom (font multiplier, default 100%) so text stays readable at any board zoom, rather than shrinking with the camera. The wheel while the pointer is over a card scrolls that card's content (the editor's native scroll, clamped to content height); the wheel over empty canvas zooms the camera. A card's scroll position is stable across content changes — typing in a tab that edits the same note doesn't reset the card's scroll. The per-card zoom is adjusted from the card's right-click menu (Zoom in / out / Reset) or Ctrl/Cmd+wheel. [canvas-card-scroll, canvas-card-zoom]
- **Inline editing.** Cards are editable in place. A card renders read-only by default; **double-clicking a full-detail card enters edit mode** — the card's body becomes a focused editor that captures keyboard + pointer (an overlay above the canvas interaction surface, positioned over the node's screen rect and tracking it on pan/zoom). The overlay opens at the card's current scroll position (no jump to top). Edit mode exits on Esc, a click outside the overlay, selecting another node, or the node scrolling off-screen. Two write paths by kind: [canvas-inline-edit]
  - **File node** → edits the referenced note through the reusable embedded buffer view (`embedded-buffer-view`): the card attaches to the one shared `session.buffers[path]` editor, so typing on the canvas shows in any open tab of that note (and vice versa), there is only one dirty buffer, and save / autosave / agent-review work identically. The card keeps its own scroll/zoom; cursor and undo are the note's.
  - **Text node** → edits the node's own `text` (which lives in the `.canvas` itself, not a vault note), committing through `canvas-edit-ops` `SetText` on the canvas document — no shared-buffer machinery needed.
  - **Read path.** Even outside edit mode, a file-node card reads the *live* shared buffer when one is loaded (showing a note's unsaved edits), falling back to disk otherwise — so an open, dirty note never looks stale on the canvas. A **LOD placeholder** (`canvas-lod-placeholder`) is too small to edit, so double-clicking one opens the note in a tab instead of entering edit mode.
  - **Save routing.** Ctrl/Cmd+S while editing a File card saves *that note's* buffer (folding its `working` layer to disk); otherwise — including while editing a Text node, whose text lives in the `.canvas` — it commits the canvas document. The chord is consumed in the Canvas view so it doesn't double-fire with any global save.
- **Context menu.** Right-click dispatches on what it hits: a node → content zoom + Delete; an edge → Edit label + Delete; empty canvas → the toolbar verbs (Add text / Add link… / Insert from vault… / New note / Add group / Fit to content), so the toolbar is reachable without leaving the canvas. [canvas-context-menu]
- **Delete.** Delete/Backspace removes the selection; removing a node cascades its incident edges. Edges are selectable (the hit-test samples the drawn Bézier, so a bowed connector is clickable) and deletable via Delete or the right-click Delete verb, as are nodes. **The canvas key shortcuts (Delete/Backspace, Ctrl-Z / -Shift-Z, Esc) act on canvas nodes only when no text editor holds keyboard focus**: while a card is in inline-edit mode (or the edge-label editor is open) the focused editor owns those keys, so Backspace deletes text rather than the node. [canvas-delete]
- **Undo/redo.** An in-session stack of inverse edit ops (Ctrl/Cmd-Z / -Shift-Z). Distinct from op-log history: undo operates on the in-memory model before Save; once committed, op-log version history (`op-log-history-materialization`) is the durable record. [canvas-undo-redo]


## Node content engines

Node *frames* are the adapter's job; node *contents* reuse hiker's existing renderers, wired by the app so the adapter stays free of the heavy engine deps. [canvas-node-content-trait]

The adapter calls a host-supplied `NodeContentRenderer` with the node and its on-screen rect; the app implements it by dispatching on kind:

- **Text node → markdown.** Rendered through the editor widget (`editor-egui`) with the live-preview decoration providers (`live-preview.md`), so a text node gets the same markdown rendering — and, in edit mode, the same editing — as a note buffer. Editing a text node writes back through `canvas-edit-ops` `set_text`, not through a separate op-log document. [canvas-text-node-markdown]
- **File node → embed.** Embeds the referenced vault file by type: a markdown note (or the extract sidecar for a PDF / audio / office source) renders as live-preview markdown (optionally scoped to the `subpath` heading/block), an image renders the image, a vault-internal `.html` / captured page renders through `hiker-htmlview` (the `htmlview-render` surface, same no-JS engine the ZIM viewer uses — consistent with `extract-web-no-js-stance`), and a code/text source renders read-only. The path resolves against the vault; an unresolvable path renders a broken-reference card, the kanban `board-card-references` posture. [canvas-file-node-embed]
- **Link node → card.** A link node is a card showing the URL with an open glyph. Because the canvas interaction surface owns pointer input (node content is display-only), opening is a *double-click* activation: the host opens the URL in the OS browser (`ctx.open_url`); double-clicking a file node opens the referenced file in a tab. Hiker does **not** live-fetch or render an external web page inside a canvas — a vault-internal `.html` page is the separate file-node case above. [canvas-link-node-card]

The seam keeps the swappability the project favors: a different content engine for any kind is an app-side change behind one trait, and the adapter/core never learn about markdown, images, or HTML.


## Vault, tab, and navigation

- **Document kind.** A `.canvas` file is an op-log document under a new `canvas` kind in `meta.kind` (the Y.Map already carries `kind` per `op-log-document-shape`). Op-log bootstrap (`op-log-doc-id-bootstrap`) walks `.canvas` files alongside `.md` notes, minting a `doc_id` and seeding the Yrs Doc from the file's JSON bytes. There is no markdown frontmatter, so every edit is an ordinary `Replace` op (no `SetFrontmatter`). [canvas-doc-kind]
- **Tab.** `TabKind::Canvas { path }` — a per-doc tab (not a singleton), opened by clicking a `.canvas` row in the file tree. Dispatched by `tabs::body` like any other tab kind. [canvas-tab]
- **View toggle.** A "View as: Canvas / JSON" control flips the pane between the spatial editor and the standard editor widget over the raw `.canvas` text (JSON highlighting via the existing `tree-sitter-json`), both over the one op-log document — the `board-view-toggle` shape. [canvas-view-toggle]
- **Op-log binding.** In Canvas view, an edit re-serializes the model (`canvas-canonical-json`), diffs against `materialize(accepted + working)`, and applies the minimal text delta as `user` ops on `working` via `core::ops` user-save — the kanban `board-move` path. The reverse direction (a synced remote edit or external file change advancing `accepted`) re-parses the current materialized JSON into the model and re-renders; **selection and camera survive by stable node `id`**, not text-offset mapping, so a remote move of one node never disturbs the local selection. Save folds `working` to disk (`op-log-atomic-write`). In JSON view the standard editor binding (`op-log-editor-binding`) applies unchanged. [canvas-oplog-binding]
- **Conflict merge.** Concurrent edits ride op-log's CRDT merge: disjoint-node edits merge automatically; two devices editing the same node touch the same JSON region and surface as a conflict hunk with Keep mine / Keep theirs / Keep both (`op-log-merge-conflict`). No canvas-specific conflict mechanism. [canvas-conflict-merge]
- **Nav stack.** Opening a canvas records `NavTarget::File` on the global Back/Forward stack (`nav-stack`), interleaved with note and snapshot history like every other surface. [canvas-nav-stack]
- **Create.** A sidebar `+` action (and the cross-type new-item picker, `sidebar-new-item-button`) seeds an empty `.canvas` through a `core` create op and opens it in the canvas view with inline-rename active — the `board-create` shape. [canvas-create]
- **File tree.** `.canvas` files render with a canvas glyph and open the canvas view on click (a "View as JSON" verb is the escape hatch), mirroring how board-docs route (`board-view`). [canvas-file-tree-glyph]
- **File-ref rewrite.** When a referenced note moves, file-node `file` paths rewrite in the same transaction through the shared `wikilink-rename-rewrite` pass alongside wikilink bodies, trail waypoints, and board cards. [canvas-file-ref-rewrite]

**Indexing.** A `.canvas` file is an op-log document (synced, versioned) but is **not** markdown-chunked — the indexer still ignores it for semantic/lexical search per `index.md`'s non-markdown tolerance. Making text-node contents searchable is deferred (`canvas-search-index`).


## Deferred

- **Search over canvas contents.** Extract text-node bodies (and file-node titles) into the index so a canvas's contents are findable, via a derived projection like `board-cards-derived-table`. [canvas-search-index]
- **Drag-to-add from the file tree.** Dropping a file row (or a multi-selection) onto the canvas creates pointer file nodes at the drop point — the same gesture as a board's `board-dnd` file drop, riding the uniform vault-path drag payload (`trails-dnd-ingestion`) once it lands. The file-tree drag / multi-select plan (`files.md`, `note-multi-select` / `drag-and-drop-move`) records that canvas must accept this drop; the **Insert from vault** picker and the **Add to canvas** verb cover insertion until then. [canvas-dnd-add]
- **Navigate to a node.** A `NavTarget` that focuses a specific node id (Back/Forward into a canvas location, deep-linking a node), extending `nav-stack` beyond file granularity. [canvas-node-nav-target]
- **Minimap / overview.** A corner minimap of the whole canvas for orientation on large boards, reusing the texture-backed minimap renderer. [canvas-minimap]
- **MCP canvas tools.** A read + curate surface (`canvas_get` / `canvas_list` plus node/edge write verbs gated by `agent-write-review-mode`) so attached agents can read a canvas as context and reorganize it, the symmetric surface to `board-mcp-tools`. [canvas-mcp-tools]


## Out of scope

- **A second canvas/diagram format.** This is the JSON Canvas open format only. The draw.io family (`ideas.md` `[drawio-source-ingest]`) and Mermaid (`editor-widgets.md`) are separate source-type / widget concerns, not this editor.
- **Embedding a canvas inside a markdown note.** A canvas is its own document, not an inline widget in the live-preview layer.
- **Real-time multi-cursor presence.** Concurrent editing merges through op-log sync (eventual), not a live shared-cursor session; presence/awareness is a sync-layer concern, not this doc's.
- **Live web rendering / external fetch.** A canvas never fetches and renders an external web page; link nodes are open-externally cards. Vault-internal `.html` is the only HTML a canvas renders, through `hiker-htmlview`.
- **Frontmatter / note metadata on a canvas.** The `.canvas` file is pure JSON Canvas; hiker-namespaced metadata (tags, lifecycle) is not modeled on it in v1.
