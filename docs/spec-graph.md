# The spec graph

One **unified spec+code graph** — spec slugs, the code symbols they govern, and all their edges — viewed through **two configurable lenses** (a primary interactive pane + a corner-minimap secondary) composed in a tab **Container**. Specs become first-class nodes you **select to reveal their edges** — not a fill overlay on code, nor only note-grain edges in the vault graph ([[spec:vault-graph-spec-edges]]). Each lens chooses what it draws and lays out its own filtered subset on its own single force-layout engine, re-running the layout when you change filters. The same graph feeds a hover preview on spec/code links.

The headline decisions:

- **One unified graph universe.** A single typed graph of spec-slug nodes + code-symbol nodes and every edge kind (spec→spec reference, spec→code governs, code→code calls/implements/typeref), built once as a `graph_view::Source`. The lenses are filtered views of this one universe — not separate graphs. [spec-graph-source]
- **No overlays — direct channels.** Node fill is always entity kind; governance drift shows directly as a `Governs`-edge colour; git "changed vs HEAD" shows directly as a node ring (full = body changed, dim = file churned around it); spec status + open bugs ride the badge marks. Selecting a spec node highlights its edges through the engine's own selected-node highlight — no whole-graph recolour mode. [spec-graph-source]
- **Spec→spec edges are wikilinks, not a new authoring concept.** A `[[spec:slug]]` in a spec doc body *is* the edge — attributed to the nearest-preceding `[slug]` anchor (the same association reconcile's link lines and the `status::` scan use, `code.md` [[spec:code-graph-status-badge]]), target resolved through the spec-anchor index ([[spec:wikilink-spec-links]]). The slug-grain twin of the vault graph's note-grain spec edges. [spec-graph-source]
- **Spec→code edges are the `links.json` baseline, adapter-free.** The `implements`/`touches` targets fold at governance build time, bound onto the existing code nodes (a target outside the index simply draws no edge — one universe, no phantom code nodes). [spec-graph-source]
- **Filtering re-runs the force layout, with edge-lifting + orphan-hiding.** Each lens builds a filtered + reindexed *display subgraph* and lays THAT out — toggling a filter rebuilds the visible set and re-settles it (the old code-graph feel), paying only for what's on screen. Hiding a kind **lifts** its edges to the nearest visible ancestor (a hidden method's calls re-attach to its type, via the `EntityNode.parent` containment chain) so connectivity survives instead of orphaning, and overview scope **hides degree-0 nodes** (the disconnected ring) unless "Show disconnected" is on. [spec-graph-shared-layout]
- **Two lenses over one shared doc, in a tab Container.** The code-graph tab is a `Container { primary, secondary, swapped }`: a shared `CodeGraphDoc` (per `CodeSource`) holds the full graph + governance + palette + importance + the shared `selected`/`hover_specs`, and each visible lens is a `LensView` with its OWN single force-layout engine. Each pane selects which node kinds and which edge kinds it draws from the universe and keeps its own view options (sizing, only-changed, drill scope) — persisted per lens. The corner minimap renders the secondary lens's engine through a borrowed-engine seam; clicking it swaps which child is the live interactive pane. [spec-graph-lens] [spec-minimap-swap]
- **Hovering a spec/code link previews its 1-hop neighbourhood.** A `[[spec:…]]` or `[[code:…]]` pill shows a mini graph of the link target's 1-hop slice of the universe, reusing the note-preview hover plumbing ([[spec:preview-note-hover]]). [spec-link-preview]

Each lens is a filter over it ([[spec:spec-graph-lens]]), never a second graph — so the panes can never disagree about what a node is or where it sits. [spec-graph-source]

| Element | Source |
| ------- | ------ |
| spec nodes | spec slugs from `Governance::specs()` ∪ the `spec_anchors` index (a `[slug]` anchor is a spec node even with no code links) |
| code nodes | the code symbols (the `CodeGraph`'s nodes — the spec's `implements`/`touches` targets are a subset) |
| spec→code edges | `Governance::targets_of(spec)` — the folded `links.json` baseline, no adapter |
| spec→spec edges | `[[spec:slug]]` body wikilinks, attributed to the nearest-preceding `[slug]` anchor, target resolved via `spec_anchors` |
| code→code edges | the code graph's own calls / implements / typeref edges ([[spec:code-graph-source]]) |
| node status / size | `Governance::status_of(spec)` colours spec nodes; structural importance (subtree + descendant connectivity) drives the default radius, `GraphNode.lines` the opt-in size-by-LOC mode ([[spec:spec-graph-node-sizing]]) |

- **Relation typing rides the inline field, optionally.** A `[[spec:x]]` authored as a `relation:: [[spec:x]]` inline field carries that relation (e.g. `belongs_to`); a bare `[[spec:x]]` in prose is a generic reference edge. No frontmatter mechanism — identical grain to spec→code's `implements:: [[code:…]]`. [spec-graph-source]
- **A `one_hop(node)` slice** returns the node plus its direct neighbours and the edges among them — the unit the link preview renders and the seed for a focus drill. [spec-graph-source]

This does not replace its two neighbours: [[spec:vault-graph-spec-edges]] draws spec→spec at *note* grain inside the vault graph; [[spec:code-graph-spec-lighting]] lets you select a spec node to glow its governed code. The unified graph is the surface where the spec slug itself is a node and the spec→code link is an edge.

A shared `CodeGraphDoc` (one per `CodeSource`) holds what both lenses must agree on; each visible lens is a `LensView` carrying its OWN single force-layout engine. [spec-graph-lens]

- **Each lens selects entities + edges.** Per-kind toggles (spec, code:type, code:function, …) auto-populated from the kinds present + per-edge-kind toggles (Calls / Impl / Governs / Refs) per lens — the generalization of the code graph's own per-kind toggles ([[spec:code-graph-kind-filters]], [[spec:code-graph-edge-toggles]]) to the spec+code universe. [spec-graph-lens]
- **Each lens persists its own view options.** Sizing ([[spec:spec-graph-node-sizing]]), the only-changed predicate, the kind/edge selection, bundling, and the drill scope are stored per lens (two `LensState` configs per `CodeSource`, in `CodeGraphViewState`) so the primary and secondary keep distinct, restart-surviving setups. [spec-graph-lens]
- **Sensible defaults.** Primary = the higher-altitude kinds (packages / spec documents / types / modules / functions + specs) + all edges, the leaf members off; secondary = specs only (the "spec map"). Both freely reconfigurable; clicking the minimap exchanges which child is primary. [spec-minimap-swap]
- **The corner minimap renders the secondary lens through a borrowed engine.** There is exactly ONE engine per lens — the old third Minimap-owned engine is gone. The `Minimap` chrome owns no engine; it renders the secondary `LensView`'s own engine + positions through the borrowed-engine seam (`Minimap::ui_for`, engine-level [[spec:graph-minimap-chrome]]), saving and restoring that engine's main-view chrome so the same engine still renders faithfully when swapped to primary. The minimap **navigates** the main view: clicking a minimap dot recenters the primary (`State::center_on`) + selects on that node; expand→collapse reports a focus the host recentres on. The minimap now opts into the engine's label budget LOD (`Minimap::set_labels`), so the corner shows the top handful of labels (specdoc containers + a few top specs) where it used to show none. Lens-swap is a button inside the Minimap dropdown. A code node's right-click menu offers Open source / Open diff / Copy symbol / **Highlight 1/2/3 hops** ([[spec:code-graph-spec-lighting]]); a SPEC node's offers **Open spec doc** (its defining note, in a preview tab) + Copy slug. [spec-minimap-swap]
- **Per-kind + per-edge colours are user-overridable.** Each entity-kind and (non-Governs) edge-kind row in the Filter dropdown leads with a clickable colour swatch (egui's drawn colour button — left-click picks, right-click resets to the built-in); overrides persist per view (`CodeGraphViewState.palette`, applied via `EntityGraphSource::with_palette`). Governs keeps its drift colouring (ok/drifted/missing), not a single hue. [spec-graph-lens]
- **Labels are a constant-size, budgeted overlay.** Label sizing + density is the engine-level constant-font budget LOD ([[spec:graph-label-budget]]): labels never scale with zoom, the budget is placed highest-importance-first, and a small filtered subgraph shows most labels. The code graph feeds that LOD its structural-depth gate + per-id importance; the minimap rides the same budget. This lens doc owns only the per-kind importance/depth mapping; the budget mechanics live at the engine layer. [spec-graph-lens]
- **Selection is a focus spotlight (dim the rest), not an additive glow.** Selecting a node dims everything else to a faint ghost (~12% — `EntityGraphSource::with_focus`, the dim-the-rest pattern graph UX uses) while the selection's footprint stays full: a CODE node lights itself + its **configurable 1/2/3-hop** neighbourhood (default 1, set from the node right-click "Highlight N hops"); a SPEC lights itself + every entity it governs — and those governed entities are **revealed into the display even if their kind is filtered out** (`filter_for`'s `force_show`, which re-runs the layout), so the footprint is complete instead of mostly-hidden. This is the full-overview spotlight, NOT the filtered `Scope::Hops` drill ([[spec:code-graph-scope-hops]]). Clicking empty background clears the selection (`State::take_background_click`); in a Hops drill that clears the highlight but stays in the filtered view, since the drill anchor (`hops_anchor`) is stored separately from the live selection. [code-graph-spec-lighting]
- **Idle-cheap.** Layout + per-frame draw run over the filtered display subgraph, not the whole universe; the engine also only re-captures warm-seed positions while the force worker is settling (`mod.rs` ui, guarded on `worker.is_running`) rather than cloning every node's key each idle/mouse-move frame. [spec-minimap-swap]

## Containment tiers, bundling, and layout

The unified graph reads as a structural map: synthetic container tiers roll members up at the overview, a containment-aware force layout clusters members around their container, and an opt-in spatial bundling further declutters. The default view is the **full dense graph** — every node, decluttered only by the label budget — with bundling an explicit simplification.

- **Crate/package tier.** A synthetic `code:package` container node is created per distinct SCIP **package** (the moniker's package field — language-agnostic: crate for Rust, npm/Python package for TS/Python, Go module path, Java artifact), parenting the top-level code modules and positioned over its members' centroid (it carries no edges, so its force position would be junk). Synthesized only when **≥2** distinct packages exist — a single-package SCIP is unchanged (top modules stay the structural roots). [entity-graph-package-tier]

## The Specs activity panel

A left-bar activity (`spec_panel`) that browses a project's specs and drives the centre code graph — the spec-first companion to exploring from the graph outward.

- **Project → nested spec list.** A project picker; its specs are listed **nested by defining doc → section heading → slug** (the way they're authored): `parse_doc_sections` walks `#` headings + `[slug]` anchors (`governance::slug_in_line`), docs scoped to the project's `…/docs` (`project_docs_prefix`). [spec-activity-panel]
- **Hover highlights, click selects.** Hovering a spec row lights its governed footprint in the graph as a **transient** focus spotlight — no reveal, no relayout (`code_graph_hover_spec` → the shared `CodeGraphDoc.hover_specs`, consumed each frame; `lens::focus_set` uses the effective `hover_specs || selected`). Clicking opens that project's code graph and selects the spec (the full reveal). The cross-panel link is the standard deferred-effect pattern (`ctx.defer` → `code_graph::{open,select_spec}`). [spec-activity-panel]

## Node sizing

The default node radius is `4 + K·importance` where importance is a structural blend (containment-subtree size + aggregated descendant connectivity, log-normalized 0..1) — so packages and hub modules read big and leaf symbols stay small dots, which is also what the on-screen-radius label gate then labels at the overview. **Size-by-LOC** is the opt-in lens mode (the spec analogue of the code graph's [[spec:graph-size-by-loc]]): a √-scaled radius over `lines` — for a spec, the `[slug]`-section length; for code, the SCIP body span. [spec-graph-node-sizing]

note:: LANDED: default is structural IMPORTANCE — `EntityGraphSource::radius` = `4 + IMPORTANCE_RADIUS_K · importance`, importance from `entity_graph::label_importance` (a size+connectivity blend accumulated UP the `parent` chain, log-normalized, cached per id on the doc). Size-by-LOC is the lens's `size_by_loc` toggle: `4 + 9·√(lines/max)`, area ∝ LOC. `EntityNode.lines` carries a spec node's `[slug]`-section span (anchor line → next `[slug]` / EOF) or a code node's SCIP `enclosing_range` body span; degree-weighting is the last fallback when no importance map is supplied · evidence: `app/src/panels/entity_graph/mod.rs` (`radius`, `IMPORTANCE_RADIUS_K`, `label_importance`)

- **Importance (default)** — the log-normalized subtree-size + descendant-connectivity blend (`label_importance`), so structurally-significant nodes read large. [spec-graph-node-sizing]
- **LOC (opt-in)** — `EntityNode.lines`: a spec's `[slug]`-section length (how much spec *text* defines it) or a code symbol's body span. √-scaled so area, not radius, tracks the metric. [spec-graph-node-sizing]

## Deferred

- **Typed spec→spec relations as edge colours.** Render `belongs_to` / `parent` relations (when authored as inline fields) with distinct hues + a legend toggle, mirroring the vault graph's [[spec:vault-graph-edge-toggles]]; the lens edge filter draws spec→spec as one generic kind for now.
- **A vault-native link store.** The spec→code half reads each project repo's committed `links.json`; a vault with no project repo carrying a baseline has no spec→code edges (the same gap [[spec:vault-graph-spec-drift-badge]] names). A vault-side link store would close it.
- **Equal-weight second interactive lens.** Each lens drills independently today — a `LensView` carries its own `Scope`/`hops_anchor` over the shared focus-navigation layer ([[spec:graph-nav-shared]], [[spec:code-graph-scope-hops]]) — but the secondary is the corner minimap. A side-by-side split of two equal interactive lenses is the remaining step (tracked as Peer split panes below).
- **Peer split panes.** The two lenses are a primary + corner-minimap today; a side-by-side split (two equal interactive panes) is a later option if the corner minimap proves too small for a working second lens.

## Out of scope

- **Editing links from the graph.** The graph is a read + navigate surface; authoring stays in the spec doc body (the `[[spec:]]` / `implements:: [[code:]]` wikilinks), reconciled into the baseline ([status.md](status.md) §"Spec→code links").
- **A separate spec-only authoring kind.** Specs stay `[slug]` anchors in docs ([[spec:wikilink-spec-links]]); the graph derives from those (the gap [[spec:vault-graph-spec-edges]] already names).
